下面这版可以作为你们后续开发的“工程纲领”，也可以改写成 README、项目计划书、答辩介绍稿。

**项目定位**

HWpilot 不应该定位成一个泛泛的“AI 作业助手”，而应该定位成：

> 面向程设课程的 AI 辅助作业版本管理与复盘系统。

它的核心不是“我能和 AI 聊天”，而是：

> 学生每完成一次作业阶段性修改，都可以提交一个真实版本；系统记录代码快照、变更内容、编译/测试结果、AI 批改反馈，并在学期内沉淀为可复盘的学习档案。

一句话卖点：

> HWpilot 把“写作业、提交版本、获得反馈、修正问题、期末复习”串成一个闭环，而不是一次性的 AI 问答工具。

**核心目标**

第一目标：把程设作业的开发过程保存下来。  
不是只保存最后代码，而是保存每一次阶段性版本、每一次 AI 反馈、每一次错误修正。

第二目标：让 AI 批改有上下文。  
AI 不只是看一堆文件，而是结合作业要求、代码变更、编译错误、测试结果和历史反馈给建议。

第三目标：让学生能复盘自己的薄弱点。  
系统需要从多次作业、多次反馈中总结出学生常犯错误，比如边界条件、内存管理、递归、类设计、代码风格等。

第四目标：降低初学者使用 Git 和 AI 的门槛。  
用户不需要手动敲复杂 git 命令，也不需要自己组织 prompt。软件替他完成“提交、比较、询问、记录、总结”。

**目标用户**

主要用户是程设课程学生，尤其是：

- 不熟悉 Git，但需要管理作业版本的学生。
- 写完代码后不知道哪里有 bug 的学生。
- 想在提交前获得一次“助教式批改”的学生。
- 期末想回顾自己常犯错误的学生。

次要用户是课程助教或老师，可以用它演示如何做版本化学习、过程性反馈和编程复盘。

**核心功能闭环**

完整流程应该是：

1. 新建或打开一个作业项目。
2. 填写作业要求、评分标准、课程资料摘要。
3. 扫描项目文件，并让用户确认哪些文件纳入管理。
4. 初始化或连接真实 Git 仓库。
5. 学生修改代码后，系统展示本次变更 diff。
6. 用户点击“编译/测试”，系统收集错误信息和运行结果。
7. 用户点击“AI 批改”，系统把作业要求、相关代码、diff、错误信息一起发给 AI。
8. AI 返回结构化反馈：问题、位置、严重程度、修改建议、知识点标签。
9. 用户把反馈保存到当前版本。
10. 用户提交一个真实版本，生成 commit。
11. 多次作业之后，系统根据历史反馈生成复习报告。

这个闭环才是 HWpilot 的主体。其他功能都应该服务这个主体。

**必须实现的功能**

项目管理：

- 打开作业项目文件夹。
- 保存项目配置，例如项目名、路径、作业要求、课程信息。
- 下次启动后能恢复最近项目。
- 每个项目有 `.hwpilot` 数据目录，保存 HWpilot 自己的元数据。

文件扫描：

- 扫描代码文件、文档文件、构建文件。
- 尊重 `.gitignore` 或至少默认排除 `build`、`.git`、缓存目录。
- 显示文件大小、语言类型、是否纳入 AI 分析。
- 支持文件预览。
- 对总输入长度做限制，避免一次性把整个项目粗暴塞给 AI。

真实版本控制：

- 如果项目没有 git 仓库，支持一键初始化。
- 支持提交版本，用户可以输入提交说明。
- 提交时调用真实 git commit。
- 左侧版本树展示真实 commit 历史，而不是 UI 假节点。
- 支持查看某次提交的文件变化。
- 支持查看当前工作区和上次提交的 diff。
- 高阶目标：支持恢复某个文件到历史版本。

变更视图：

- 显示新增、修改、删除文件。
- 显示关键 diff。
- 在 AI 批改时优先分析本次变更，而不是每次全量分析。
- 这是你们区别于普通 AI 聊天工具的重要卖点。

编译与测试：

- 支持用户配置编译命令，例如 `cmake --build build`。
- 支持运行测试命令，例如 `ctest` 或自定义命令。
- 捕获 stdout、stderr、退出码。
- 把编译错误、运行错误和测试失败交给 AI 分析。
- 这是“AI 反馈可信度”的重要来源。

AI 批改：

- 不只是换 prompt，而是针对不同模式组织不同输入。
- 代码批改：作业要求 + 代码 + diff + 历史反馈。
- Bug 检查：编译结果 + 运行日志 + 相关代码。
- 启发式引导：只输入作业要求，不直接给完整答案。
- 学习模式：输入知识点问题和课程资料。
- 复习总结：输入历史反馈数据库，而不是当前文本框内容。

反馈管理：

- AI 输出不能只是一整段纯文本。
- 应该保存为结构化数据：标题、文件、行号、严重程度、建议、知识点标签、状态。
- 用户可以标记“已解决”“暂不处理”“误报”。
- 每个版本都能看到对应反馈。
- 每个反馈都能关联到某次 commit。

复习报告：

- 汇总所有作业中的反馈。
- 统计常见问题类型。
- 找出高频薄弱知识点。
- 给出复习建议。
- 生成相似练习题。
- 最好能导出 Markdown 或 HTML 报告。

**建议的功能分层**

第一阶段，保证主线能跑：

- 项目打开
- 文件扫描
- Git 初始化和提交
- Diff 展示
- AI 批改
- 反馈保存
- 历史版本查看

第二阶段，增强可信度：

- 编译命令配置
- 运行测试
- 编译错误 AI 分析
- 结构化反馈列表
- 反馈状态管理

第三阶段，形成大作业亮点：

- 复习报告生成
- 知识点标签统计
- 历史薄弱点趋势
- 文件级/版本级回溯
- 更完整的 UI 打磨（新手教程）

**主要卖点**

卖点一：AI 和 Git 结合。  
普通 AI 工具只看当前代码，HWpilot 能看历史版本和本次变更。

卖点二：作业过程可追踪。  
学生不是只提交最终结果，而是能看到自己如何一步步修正问题。

卖点三：反馈可沉淀。  
每次 AI 批改都会变成学习记录，最后生成复习报告。

卖点四：面向程设课场景。  
不是通用 IDE，不是普通聊天机器人，而是围绕作业要求、代码、编译错误、版本提交设计。

卖点五：降低 Git 使用门槛。  
学生通过图形界面完成 commit、diff、历史查看，逐步理解版本控制思想。

**主要难度**

第一难点是真实 Git 集成。  
不能停留在“版本树 UI”。要真正调用 git，处理仓库不存在、未提交改动、提交失败、冲突、历史查看等情况。

第二难点是 AI 上下文组织。  
不能无脑塞所有文件。要选择相关文件、diff、错误日志、作业要求，并控制上下文长度。

第三难点是反馈结构化。  
AI 天然输出自然语言，但系统需要把它变成可保存、可筛选、可统计的数据。

第四难点是持久化设计。  
版本、反馈、报告、用户配置都要保存。否则程序一关，学习档案就消失。

第五难点是 UI 流程打磨。  
用户应该清楚知道当前处于哪一步、下一步该做什么、哪些反馈还没处理。

第六难点是“复习总结”的真实性。  
复习报告不能凭空生成，必须基于历史反馈、知识点标签和提交记录。

**当前 naive 的地方要修正**

不要把“接入 AI API”当成核心创新。  
真正的创新是 AI 如何结合代码变更、编译结果和学习历史。

不要把“添加版本节点”当成版本控制。  
版本控制必须能保存、比较、恢复。

不要用多个 prompt 模式假装功能丰富。  
每个模式必须有不同的数据输入、输出结构和使用场景。

不要把 UI 做成按钮集合。  
要做成任务流：打开作业、查看变更、分析问题、保存反馈、提交版本、复习总结。

不要追求功能越多越好。  
重点是把“版本 + AI 反馈 + 复盘”这条主线做深。

**最终效果应该是什么样**

用户打开 HWpilot 后，看到的是一个当前作业工作台：

- 左侧是项目和真实版本历史。
- 中间是当前文件、变更 diff、编译/测试结果、历史反馈。
- 右侧是 AI 助教面板和结构化问题列表。
- 顶部显示当前项目状态：是否有未提交修改、最近一次提交、测试是否通过、待解决问题数量。

一次典型演示应该是：

> 打开一个有 bug 的 C++ 作业项目，系统扫描文件，显示当前修改；点击编译发现错误；点击 AI 分析，AI 指出错误位置和原因；用户保存反馈并提交版本；再修改代码后重新编译通过；最后生成一次版本记录和学习反馈。

这才是一个有说服力的大作业演示。



说狠一点：现在它是“能跑的功能原型”，但还不像一个完成度高的大作业。最大问题不是 Qt 写得差，而是产品目标太散、核心闭环太浅、很多地方是“看起来有这个功能”，但没有真正承担这个功能的复杂度。

**1. 定位模糊**

你们现在同时想做：

- 作业项目管理器
- Git 版本控制工具
- AI 代码批改工具
- 学习模式聊天助手
- 复习报告生成器
- 课程资料/PPT 总结工具

这几个方向每个都能单独做成一个大作业。现在放在一起，容易变成“每个都有按钮，每个都不深”。

比较 naive 的地方是：你们把“用户可能需要的能力”都列出来了，但没有回答一个更关键的问题：用户每天打开这个软件时，到底完成哪一个不可替代的任务？

更好的定位应该收窄成一句话，比如：

> HWpilot 是一个面向程设作业的 AI 辅助版本管理工具：每次提交代码时，自动记录代码快照、AI 反馈、问题标签，并在期末生成个人薄弱点报告。

这样所有功能都围绕“提交记录 + AI 反馈 + 复盘”展开，老师也容易理解。

**2. 版本控制目前是伪功能**

README 说“版本节点管理”，UI 里也有“提交版本”，但实际只是往 `QTreeWidget` 加一个节点：[MainWindow.cpp](/Users/yangruochen/Desktop/HWpilot/MainWindow.cpp:302)。没有真实 git commit，没有 diff，没有 checkout，没有恢复文件，没有分支，没有持久化。

这会被老师一问就穿：

> 你这个提交版本和真的保存版本有什么区别？

现在答案其实是：只是界面上多了一行。

你们一开始“把不同作业理解成不同分支”这个想法也有点 naive。Git 分支适合并行开发线，不一定适合作业分类。更自然的是：

- 每个作业是一个 project 或 workspace。
- 每次提交是一次真实 git commit。
- AI 反馈挂在 commit hash 上。
- 版本树展示真实 `git log --graph`。
- 变更视图展示真实 diff。
- 支持恢复某个文件到某次提交。

最低限度也应该做：初始化 git、提交、查看 log、查看 diff、checkout 单文件。否则“版本控制”最好不要作为主卖点。

**3. AI 功能停留在“把文件塞给模型”**

现在 AI 分析的核心逻辑是拼一段 prompt，然后发给 DeepSeek：[MainWindow.cpp](/Users/yangruochen/Desktop/HWpilot/MainWindow.cpp:359)、[HWpilotLLM.cpp](/Users/yangruochen/Desktop/HWpilot/HWpilotLLM.cpp:17)。

这个能演示，但深度不足。问题在于：

- 没有 token 预算，文件多一点就可能超上下文。
- 没有按文件重要性筛选。
- 没有把编译错误、测试结果、git diff 一起给 AI。
- 没有结构化解析 AI 输出。
- 没有保存多轮对话，只保存当前版本一段反馈。
- 没有区分“批改作业”和“问知识点”的交互形态。
- 没有 timeout、HTTP 状态码、JSON 解析失败处理；成功请求但没有 `choices` 时也不会报错：[HWpilotLLM.cpp](/Users/yangruochen/Desktop/HWpilot/HWpilotLLM.cpp:39)。

更成熟的 AI 辅助应该是：

1. 先扫描项目。
2. 自动编译/运行测试。
3. 获取 git diff。
4. 只把相关文件、错误信息、作业要求发给模型。
5. AI 输出结构化结果：问题、严重程度、文件、行号、建议。
6. 用户可以把某条反馈标记为“已解决/忽略/待处理”。

否则 AI 模块只是“带文件上传的聊天框”。

**4. 缺少真实数据持久化**

现在版本节点、AI 反馈、扫描结果都在内存里。程序一关，基本就没了。`saveFeedbackToVersion()` 只是写进 `QTreeWidgetItem` 的 `UserRole`：[MainWindow.cpp](/Users/yangruochen/Desktop/HWpilot/MainWindow.cpp:427)。

这对大作业很伤，因为“作业管理”“版本历史”“复习报告”全都依赖长期数据。

应该有一个明确的数据层，比如：

- `.hwpilot/project.json`
- `.hwpilot/feedbacks/<commit-hash>.json`
- `.hwpilot/reports/*.md`
- 或 SQLite

至少要保存：

- 项目路径
- 作业名称
- 每次版本提交时间
- commit hash
- AI 反馈
- 用户标记的问题类型
- 复习总结结果

没有持久化，很多功能只能算 UI demo。

**5. 文件扫描太简单**

`HWFileScanner` 现在按扩展名递归读文件：[HWFileScanner.cpp](/Users/yangruochen/Desktop/HWpilot/HWFileScanner.cpp:33)。这很直观，但工程上偏粗糙。

问题包括：

- 不读 `.gitignore`，可能扫进 build 产物、第三方库、缓存文件。
- 只按单文件 200KB 限制，不按总 token 限制。
- 默认 UTF-8，遇到 GBK/混合编码可能乱码。
- 没有文件预览，用户不知道 AI 到底会看到什么。
- 没有按语言/目录筛选。
- 没有排除 `build`、`cmake-build-debug`、`.vscode`、`__pycache__` 等常见目录。
- `fileInfo.absolutePath().contains("/.")` 这种判断有误伤风险：[HWFileScanner.cpp](/Users/yangruochen/Desktop/HWpilot/HWFileScanner.cpp:52)。

更好的扫描器应该像一个 mini 项目索引器：尊重 ignore 规则，统计大小，显示 token 估计，允许用户预览和排除文件。

**6. UI 是统一了颜色，但体验还没有成型**

现在 UI 看起来是三栏：左侧项目/版本，中间 tab，右侧 AI 面板。结构还可以，但体验上有几个明显问题：

- 第一次打开不知道下一步该干什么。
- “文件”tab 只有列表，没有文件内容预览。
- “变更”tab 是占位文本：[MainWindow.cpp](/Users/yangruochen/Desktop/HWpilot/MainWindow.cpp:275)。
- “复习报告”其实显示的是当前版本 AI 反馈，命名不准确。
- “提交版本”没有让用户输入提交说明。
- AI 分析没有取消按钮。
- AI 输出是纯文本，不渲染 Markdown。
- API Key 要求用户设置环境变量，对普通用户不友好。
- 工具栏全是文字按钮，没有图标、状态、禁用逻辑。

更好的 UX 应该围绕一个清楚流程：

打开作业 -> 扫描 -> 查看变更 -> 编译/测试 -> AI 批改 -> 生成问题清单 -> 提交版本 -> 复盘报告。

现在是“功能摆在界面上”，还不是“引导用户完成任务”。

**7. UI 风格只是表层统一**

`applyStyle()` 里全局 QSS 统一了灰白蓝：[MainWindow.cpp](/Users/yangruochen/Desktop/HWpilot/MainWindow.cpp:185)。这不算坏，但有点“套皮”。

不统一主要体现在信息层级：

- 左侧树、中间 tab、右侧 AI 面板都差不多重，没有主次。
- 输入框、反馈框、文件列表视觉权重接近。
- “复习报告”“提交记录”“变更”这些页面都是 HTML 字符串堆出来的，缺少专门组件。
- 按钮文案都是平级动词，看不出主操作。
- 固定高度输入框在不同屏幕上可能不舒服：[MainWindow.cpp](/Users/yangruochen/Desktop/HWpilot/MainWindow.cpp:160)。

应该让“当前作业状态”和“下一步操作”最突出。比如顶部显示当前项目、当前 git 状态、最近一次提交、AI 待处理问题数量；右侧 AI 是辅助区，不应该抢完整主流程。

**8. 架构上 MainWindow 太重**

`MainWindow.cpp` 470 行，里面混了 UI 创建、项目状态、扫描、版本节点、AI prompt 拼接、请求回调、HTML 生成。现在还能忍，但继续加功能会迅速失控。

更成熟的拆法：

- `ProjectManager`：打开项目、保存项目配置。
- `GitService`：commit、diff、log、checkout。
- `FileScanner`：扫描和过滤。
- `AiService`：请求、错误处理、模型配置。
- `FeedbackStore`：保存 AI 反馈。
- `ReportGenerator`：生成复习报告。
- `MainWindow`：只负责连接 UI 和这些服务。

现在最大风险是：每加一个功能都往 MainWindow 塞，最后很难维护，也很难解释架构设计。

**9. 功能数量看着多，但每个功能的“完成标准”不明确**

比如“学习模式”现在只是换 prompt；“复习总结”也是换 prompt；“Bug 检查”也是换 prompt：[MainWindow.cpp](/Users/yangruochen/Desktop/HWpilot/MainWindow.cpp:337)。

这在答辩里容易被认为是“模式很多，但本质一样”。

每个模式应该有不同输入、输出和数据流：

- 代码批改：输入作业要求 + 代码 + diff，输出评分报告。
- Bug 检查：输入编译结果 + 运行日志 + 代码，输出 bug 列表。
- 启发式引导：输入作业要求，不允许读取完整答案代码。
- 学习模式：输入问题 + 课程资料，输出讲解和练习。
- 复习总结：输入历史反馈数据库，输出薄弱点统计。

现在只是 prompt 不同，产品含金量不够。

**10. 缺少“可验证”的能力**

AI 批改最大的问题是不可验证。老师可能会问：

> 你怎么知道 AI 说得对？

目前没有答案。

应该补一些非 AI 的确定性能力：

- 编译项目。
- 捕获编译错误。
- 运行测试。
- 展示测试通过率。
- 统计代码行数、文件数、函数数。
- 检查是否有 TODO、空实现、危险函数。
- 和上次提交做 diff。

这样 AI 的建议就不是凭空聊天，而是基于真实证据。

**11. 代码量确实偏少，但不是单纯行数问题**

总共约 1000 行。对课程大作业来说，不一定致命，关键看课程要求。但目前 1000 行里有相当比例是 UI 搭建和字符串拼接，核心逻辑偏少：

- Git 核心逻辑：几乎没有。
- 数据持久化：没有。
- 报告生成：没有。
- 测试运行：没有。
- 项目配置：没有。
- 错题/反馈知识库：没有。
- 用户设置：没有。

所以问题不是“少写几百行”，而是缺少能体现设计能力的模块。

**12. 你们可能想错的几个点**

第一个：以为“接入 AI API”本身就是亮点。  
现在 AI API 很常见，亮点应该是你怎么把 AI 放进一个具体学习流程里。

第二个：以为“版本树 UI”就等于版本控制。  
版本控制的核心是可追溯、可比较、可恢复，不是树状控件。

第三个：以为功能越多越像大作业。  
实际答辩更吃“一个核心功能做深”。一个扎实的“AI + Git 作业复盘系统”比五个浅功能强。

第四个：以为 prompt 模式多就是智能。  
真正的智能来自上下文组织、历史沉淀、结构化反馈、可验证结果。

第五个：以为 UI 能展示就是用户体验。  
用户体验是用户能不能少思考、少犯错、知道下一步干什么。

**最应该补的优先级**

1. 接入真实 git：init、commit、log、diff、checkout 文件。
2. 做持久化：保存项目、版本、AI 反馈、报告。
3. 做“编译/运行/测试”入口，把错误交给 AI 分析。
4. 把 AI 输出变成结构化问题列表，而不是一整段文本。
5. 重命名和收敛功能：主打“作业版本 + AI 反馈 + 复盘”。
6. UI 上强化主流程，删掉或降级暂时做不深的模式。
7. 拆分 MainWindow，补几个服务类，让架构看起来像工程项目。

我对它现在的评价是：基础方向是有潜力的，尤其“AI 反馈挂到版本节点上”这个想法不错；但目前还是“课程项目设想的第一版壳子”。想让它像一个成熟大作业，需要把“版本、反馈、复盘”这条链条真正打通。
